# План разработки собственного движка маршрутизации

Дата: 13 ноября 2026 года.

## Цель проекта

Создать движок, который умеет:

- строить автомобильные маршруты и матрицы времени и расстояний;
- возвращать время, расстояние и геометрию маршрута через упорядоченные точки;
- впоследствии строить маршруты «пешком → общественный транспорт → метро → пешком»;
- постепенно приближаться по скорости дорожных запросов к OSRM.

Начальный масштаб — небольшой район, затем один город. Работать короткими этапами: изучить необходимую теорию, реализовать, проверить результат, измерить скорость. Корректность важнее ранней оптимизации.

## 1. Освоить основу: граф и поиск пути

Изучить ориентированный граф, список смежности, очередь с приоритетом и алгоритм Dijkstra. Разобраться, чем отличаются расстояние, время и вес, который минимизирует поиск.

Реализовать маленький граф вручную, без OSM. Добавить поиск пути и восстановление последовательности рёбер. Хранить длину и время отдельно, предусмотреть недостижимые вершины.

**Результат:** программа находит самый быстрый или самый короткий путь на выдуманной сети и объяснимо проходит небольшие проверочные примеры.

## 2. Построить дорожный граф из OSM

Взять небольшой экстракт района и готовую библиотеку чтения OSM PBF. Изучить nodes, ways, relations и основные теги: highway, oneway, access, motor_vehicle, maxspeed.

Построить ориентированный граф: перекрёстки и необходимые точки разбиения становятся вершинами, дорожные участки — рёбрами. Промежуточные точки сохранить в геометрии. Учитывать направления, доступ автомобилям и базовые скорости по типам дорог. Приближённые скорости явно считать моделью, а не точным прогнозом ETA.

Сохранять построенный граф на диск, чтобы не разбирать PBF при каждом запуске.

**Результат:** поиск между вершинами реального района, маршрут можно показать на карте через GeoJSON.

## 3. Принимать произвольные координаты

Добавить пространственный индекс дорожных участков и проекцию координат на геометрию ребра. Учитывать частичные участки на старте и финише, разрешённые направления и случай двух точек на одном ребре.

Ближайший по геометрии участок может быть недоступным или изолированным: постепенно добавить выбор из нескольких подходящих кандидатов.

**Результат:** запрос с двумя координатами возвращает связный маршрут, время, расстояние и геометрию.

## 4. Учесть автомобильные повороты

Разобраться с OSM turn restrictions и стоимостью перехода между рёбрами. Добавить запреты поворотов и базовые штрафы, включая развороты.

Для ограничений поворотов состояние поиска должно учитывать входящее ребро. Сначала поддержать обычные ограничения через одну вершину; ограничения через цепочки ways выделить в отдельную задачу и явно обозначить границы поддержки.

**Результат:** маршруты соблюдают поддерживаемые ограничения. Есть проверки односторонних улиц, запрещённых поворотов, разворотов и недостижимых точек.

## 5. Добавить маршруты через точки и матрицы

Разделить три операции:

- маршрут через упорядоченные координаты — поиск с заданными правилами остановок и разворотов на промежуточных точках;
- время и геометрия известной последовательности рёбер — проход по готовому пути;
- матрица — расчёт численных результатов между множествами источников и целей.

Для матрицы сначала запускать один Dijkstra от каждого источника сразу ко всем целям, завершая поиск после нахождения всех достижимых целей или исчерпания поиска. Геометрию для каждой ячейки не восстанавливать.

Зафиксировать смысл матрицы: например, время и расстояние вдоль самого быстрого пути. Минимальное расстояние — отдельная метрика и отдельный поиск, если нужен именно кратчайший путь.

GPS-полилиния не является готовой последовательностью рёбер: её привязку через map matching отложить до появления такой потребности.

**Результат:** маршруты через несколько точек и матрицы 10×10 / 100×100 с определённой семантикой результатов.

## 6. Создать воспроизводимые проверки и бенчмарки

Сохранять небольшие искусственные графы и реальные примеры сложной топологии. Использовать базовый Dijkstra как эталон для ускоренных алгоритмов при одинаковых весах и ограничениях.

Поднять OSRM на том же регионе для сравнения маршрутов и производительности. Отличия маршрутов разбирать с учётом различий профилей, скоростей и штрафов: OSRM не является абсолютным эталоном модели собственного движка.

Измерять время подготовки данных, размер графа, память, число обработанных состояний и p50/p95 задержки. Отдельно измерять одиночный маршрут, матрицы разных размеров, поиск без геометрии и восстановление геометрии. Фиксировать оборудование, число потоков и состояние кэшей.

**Результат:** набор запросов и отчёт, по которым видно, что работает правильно и где тратится время.

## 7. Ускорить дорожное ядро

Сначала профилировать работающую реализацию. Убрать лишние аллокации из поиска, использовать компактные массивы и переиспользовать рабочую память. Добавить двунаправленный Dijkstra; A* рассматривать для одиночных запросов с корректной нижней оценкой времени.

Затем выбрать один алгоритм предобработки:

| Вариант | Когда рассматривать |
|---|---|
| CH | Фиксированные веса и приоритет очень быстрых запросов / матриц |
| MLD | Разделение топологии на области и обновление весов через customization |
| CCH | Отдельное построение иерархии и настройка под веса |

Выбор подтвердить требованиями к обновлению скоростей, памяти и времени подготовки. Произвольные веса на каждый запрос не становятся бесплатными благодаря customization.

Для матриц использовать специализированный many-to-many поиск, соответствующий выбранному алгоритму. Распараллеливание добавлять после измерений одного потока и с учётом расхода рабочей памяти.

**Результат:** измеримое ускорение без изменения ответов относительно базового поиска. Близость к OSRM оценивать на сопоставимых задачах, без заранее обещанного коэффициента.

## 8. Добавить пешеходный профиль

Использовать общую инфраструктуру OSM, геометрии и пространственного поиска. Добавить правила доступа для ходьбы: пешеходные дорожки, переходы, лестницы и направления, которые отличаются от автомобильных.

Не считать пешеходный граф копией автомобильного с меньшей скоростью: часть путей и ограничений различается.

**Результат:** корректные пешие маршруты и поиск остановок в пределах заданного времени ходьбы.

## 9. Освоить расписания на маленьком примере

Собрать выдуманную сеть: дом, пеший подход, автобус, переход, метро, работа. Добавить конкретные рейсы, ожидание и минимальное время пересадки.

Для понимания и проверки можно построить маленький граф событий: вершины — события прибытия / отправления, рёбра — поездки, ожидание и ходьба. Решить его Dijkstra и сохранить как эталон.

Изучить GTFS Schedule: stops, routes, trips, stop_times, calendar, calendar_dates, transfers, pathways, shapes. Учитывать дни обслуживания, исключения, часовой пояс и времена после 24:00. Выбрать один город с доступными и качественными данными.

**Результат:** правильное время прибытия для разных моментов отправления, включая пропущенную пересадку и переход через полночь.

## 10. Реализовать RAPTOR и связать его с ходьбой

Начать со статического расписания и базового RAPTOR: время прибытия и число поездок / пересадок. Восстанавливать рейсы и переходы по предшественникам.

Соединить пеший подход к остановкам, поездки и пересадки, пеший выход к цели. Учитывать прямой пеший маршрут. Пересадки между платформами моделировать по данным и явным правилам, а не только по близости координат.

Автобус и метро обрабатывать одной моделью рейсов; отдельные особенности задавать данными. Проверять допущения реализации о порядке рейсов и обгонах. Предрасчёт переходов должен сохранять переходы, допустимые выбранными ограничениями ходьбы.

**Результат:** маршрут «пешком → автобус → метро → пешком» с временем ожидания, пересадками и геометрией. Геометрию поездок брать из GTFS shapes, когда она доступна; обозначать приближения при её отсутствии.

## 11. Добавить мультимодальные матрицы

Первая версия — матрица для заданной даты и времени отправления. Предварительно вычислять пешие подходы источников и выходы к целям; для выходов учитывать направление пешеходного графа.

Запускать RAPTOR от каждого источника ко множеству остановок и использовать результат для всех целей. Время ячейки включает ходьбу, ожидание, поездки и пересадки. Расстояние относится к выбранному маршруту и требует определённой геометрии поездок.

Сравнивать производительность с Valhalla только после проверки поддерживаемых возможностей и одинаковых правил. Если эталон построен отдельными запросами для каждой пары, явно отметить это отличие.

**Результат:** автомобильные и мультимодальные матрицы с понятными входными параметрами и ограничениями.

## Что отложить

- Планетарный граф, распределённое выполнение и сложное тайлирование.

- Несколько пользовательских критериев, тарифы и McRAPTOR.

## Организация проекта

Начать с одной библиотеки и CLI. Выделять компоненты по мере появления: импорт данных, дорожный граф, пространственный индекс, поиск, расписания, восстановление результата. HTTP API добавить после работающего локального сценария.

Выбрать знакомый язык. Go подходит для первой реализации; C++ или Rust позволяют более явно управлять памятью. Возможность приблизиться к OSRM зависит прежде всего от алгоритмов, представления данных и реализации, а не только от языка.

Не пытаться сразу перенять архитектуру Valhalla целиком. Использовать Valhalla и OSRM как источники конкретных решений после появления собственного работающего примера.

## Материалы по порядку

1. Базовый курс алгоритмов: графы, binary heap, Dijkstra, A*.
2. OSM: элементы nodes / ways / relations, теги доступа, oneway и turn restrictions — https://wiki.openstreetmap.org/wiki/Elements
3. Локальные OSRM docs/profiles.md, docs/tools.md и документация Valhalla по costing и алгоритмам поиска.
4. Обзор «Route Planning in Transportation Networks» — после базового движка, для выбора ускорений.
5. Спецификация GTFS Schedule — https://gtfs.org/documentation/schedule/reference/
6. Статья «Round-Based Public Transit Routing» — для реализации RAPTOR.

## Ближайшая задача

Создать отдельный репозиторий. Реализовать ориентированный граф из 10–20 вершин, Dijkstra, восстановление пути и вывод расстояния / времени. Проверить ситуацию, где самый короткий путь отличается от самого быстрого, одностороннее ребро и недостижимую цель.

После этого взять небольшой OSM-экстракт и получить первый маршрут на карте. К следующему этапу переходить по работающему результату, без жёстких календарных сроков.
